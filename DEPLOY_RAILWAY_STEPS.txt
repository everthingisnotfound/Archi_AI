ARCHI AI - FRESH RAILWAY DEPLOYMENT STEPS
==========================================

Use these steps in order. Do not skip the root-directory or environment-variable steps.


1) PUSH THE CURRENT CODE TO GITHUB

Open PowerShell in the Archi_AI repository and run:

    git status
    git push origin main

The latest commits must include:

    50f76ef  fix: proxy API requests from web container
    1b58bd8  fix: prevent worker migration races
    ff0bab3  config: add Railway service deployments

If GitHub asks for authentication, complete it and repeat the push if necessary.


2) CREATE A NEW RAILWAY PROJECT

1. Open https://railway.app
2. Open the Railway dashboard.
3. Click "New Project".
4. Choose "Deploy from GitHub repo".
5. Select:

       everthingisnotfound/Archi_AI

6. Use the latest main branch.
7. Do not deploy the automatically detected services yet.
8. Rename the project to something recognizable, for example:

       Archi AI Production


3) ADD POSTGRESQL

1. Inside the new Railway project, click "New".
2. Choose "Database".
3. Choose "Add PostgreSQL".
4. Wait until PostgreSQL is running.
5. Do not manually copy the database password.
6. The other services will reference the generated variable:

       ${{Postgres.DATABASE_URL}}


4) ADD REDIS

1. Inside the same Railway project, click "New".
2. Choose "Database".
3. Choose "Add Redis".
4. Wait until Redis is running.
5. The other services will reference:

       ${{Redis.REDIS_URL}}


5) CONFIGURE THE AI SERVICE FIRST

Create a new service from the same GitHub repository:

1. Click "New".
2. Choose "GitHub Repo".
3. Select everthingisnotfound/Archi_AI.
4. Open the new service settings.
5. Rename the service to:

       ai-service

6. Open "Settings" and set:

       Root Directory: /services/ai
       Config-as-code file: /services/ai/railway.json

7. Do not set a Dockerfile.
8. Do not add a Procfile.
9. Do not set the root directory to "/".
10. Confirm the service is using Railpack/Nixpacks.
11. Deploy the service.

Set these variables on the AI service:

    PORT=${{PORT}}
    AI_PROVIDER=groq
    DATABASE_URL=${{Postgres.DATABASE_URL}}
    REDIS_URL=${{Redis.REDIS_URL}}
    INTERNAL_JOB_TOKEN_SECRET=<new random secret, at least 32 characters>
    GROQ_API_KEY=<new rotated Groq key>
    GROQ_MODEL=openai/gpt-oss-120b
    OPENAI_API_KEY=
    OPENAI_MODEL=gpt-4o-mini
    WORKSPACE_ROOT=/tmp/workspaces

Important:

- Generate a new Groq key. The previous key was exposed and must not be reused.
- Generate one new INTERNAL_JOB_TOKEN_SECRET.
- Save that exact secret somewhere secure. You will use the exact same value on
  the API and Worker services.
- Do not put real secrets into GitHub or this text file.

Verify the AI service:

1. Open the AI service "Deployments" tab.
2. Open the latest deployment logs.
3. Confirm Uvicorn starts without an error.
4. Open the AI service "Networking" tab.
5. Copy the private domain, for example:

       ai-service.railway.internal

6. The private URL used by API and Worker will be:

       http://<AI_PRIVATE_DOMAIN>:8000


6) CONFIGURE THE API SERVICE

Create another service from the same GitHub repository:

1. Click "New".
2. Choose "GitHub Repo".
3. Select everthingisnotfound/Archi_AI.
4. Rename the service to:

       api

5. Open "Settings".
6. Set:

       Root Directory: /
       Config-as-code file: /apps/api/railway.json

7. Do not set the root directory to "/apps/api".
8. Do not use a Dockerfile.
9. Do not add a Procfile.

Set these API variables:

    NODE_ENV=production
    PORT=${{PORT}}
    DATABASE_URL=${{Postgres.DATABASE_URL}}
    REDIS_URL=${{Redis.REDIS_URL}}
    SESSION_SECRET=<new random secret, at least 32 characters>
    INTERNAL_JOB_TOKEN_SECRET=<exactly the same value used on AI>
    AI_SERVICE_URL=http://<AI_PRIVATE_DOMAIN>:8000
    CORS_ORIGIN=https://<WEB_PUBLIC_DOMAIN>
    API_BASE_URL=https://<API_PUBLIC_DOMAIN>
    WEB_BASE_URL=https://<WEB_PUBLIC_DOMAIN>
    WORKSPACE_ROOT=/tmp/workspaces

Replace these placeholders:

    <AI_PRIVATE_DOMAIN>  = the AI private domain from Step 5
    <API_PUBLIC_DOMAIN>  = the public API domain generated by Railway
    <WEB_PUBLIC_DOMAIN>  = the public Web domain generated later

Use the temporary Web domain if the Web domain has not been created yet.
After the final Web domain is known, update CORS_ORIGIN and redeploy the API.

The committed API configuration must produce these commands:

    Build: npm run build --workspace @ai-archaeologist/api
    Start: npm run start --workspace @ai-archaeologist/api

Deploy the API.

Verify the API:

1. Open the API deployment logs.
2. Confirm the workspace build finishes successfully.
3. Confirm Prisma migration completes.
4. Confirm the API starts and listens on Railway's PORT.
5. Open:

       https://<API_PUBLIC_DOMAIN>/healthz

6. The endpoint must return HTTP 200 and a JSON response.


7) CONFIGURE THE WORKER SERVICE

Create another service from the same GitHub repository:

1. Click "New".
2. Choose "GitHub Repo".
3. Select everthingisnotfound/Archi_AI.
4. Rename the service to:

       worker

5. Open "Settings".
6. Set:

       Root Directory: /
       Config-as-code file: /apps/worker/railway.json

7. Do not set the root directory to "/apps/worker".
8. Do not use a Dockerfile.
9. Do not add a Procfile.

Set these Worker variables:

    NODE_ENV=production
    DATABASE_URL=${{Postgres.DATABASE_URL}}
    REDIS_URL=${{Redis.REDIS_URL}}
    INTERNAL_JOB_TOKEN_SECRET=<exactly the same value used on AI and API>
    AI_SERVICE_URL=http://<AI_PRIVATE_DOMAIN>:8000
    WORKSPACE_ROOT=/tmp/workspaces
    WORKER_CONCURRENCY=2

The committed Worker configuration must produce these commands:

    Build: npm run build --workspace @ai-archaeologist/worker
    Start: npm run start --workspace @ai-archaeologist/worker

Do not add "npx prisma migrate deploy" to the Worker start command.
The API service owns database migrations so API and Worker do not compete for
Prisma's migration lock.

Deploy the Worker.

Verify the Worker:

1. Open the Worker deployment logs.
2. Confirm the workspace build finishes successfully.
3. Confirm it starts the Worker process.
4. Confirm the Worker health server listens on Railway's PORT or configured health port.
5. Confirm there are no Prisma migration-lock errors.


8) CONFIGURE THE WEB SERVICE

Create another service from the same GitHub repository:

1. Click "New".
2. Choose "GitHub Repo".
3. Select everthingisnotfound/Archi_AI.
4. Rename the service to:

       web

5. Open "Settings".
6. Set:

       Root Directory: /
       Config-as-code file: /apps/web/railway.json

7. Do not set the root directory to "/apps/web".
8. Do not use the local Docker/nginx configuration on Railway.
9. Do not use "npm run dev".

Set these Web variables BEFORE deploying:

    NODE_ENV=production
    VITE_API_BASE_URL=https://<API_PUBLIC_DOMAIN>

The committed Web configuration must produce these commands:

    Build: npm run build --workspace @ai-archaeologist/web
    Start: npm run start --workspace @ai-archaeologist/web

Deploy the Web service.

Verify the Web service:

1. Open the Web public domain.
2. View the page source.
3. Confirm it contains a path similar to:

       /assets/index-<hash>.js

4. Confirm it does NOT contain:

       /@vite/client
       /src/main.tsx

5. Open the browser developer tools.
6. Confirm API calls go to:

       https://<API_PUBLIC_DOMAIN>


9) UPDATE API CORS AFTER THE WEB DOMAIN EXISTS

After Railway gives the Web service its final public domain:

1. Open the API service.
2. Open "Variables".
3. Set:

       CORS_ORIGIN=https://<FINAL_WEB_PUBLIC_DOMAIN>

4. Save the variable.
5. Redeploy the API service.
6. Reload the Web site in a private browser window.


10) CHECK ALL SERVICE VARIABLES

Confirm these requirements exactly:

1. API, Worker, and AI have byte-for-byte identical:

       INTERNAL_JOB_TOKEN_SECRET

2. API and Worker use the same:

       AI_SERVICE_URL=http://<AI_PRIVATE_DOMAIN>:8000

3. API has:

       DATABASE_URL
       REDIS_URL
       SESSION_SECRET
       CORS_ORIGIN
       AI_SERVICE_URL
       INTERNAL_JOB_TOKEN_SECRET

4. Worker has:

       DATABASE_URL
       REDIS_URL
       AI_SERVICE_URL
       INTERNAL_JOB_TOKEN_SECRET

5. AI has:

       DATABASE_URL
       REDIS_URL
       AI_PROVIDER
       GROQ_API_KEY
       INTERNAL_JOB_TOKEN_SECRET

6. Web has:

       VITE_API_BASE_URL

7. API, Worker, and Web are rooted at the repository root.
8. AI is rooted at /services/ai.
9. No service uses a Procfile.
10. No service uses "npm run dev".
11. No service uses the Docker Compose hostname "ai" in AI_SERVICE_URL.


11) TEST THE DEPLOYED SERVICES

Run these checks from PowerShell after replacing the domains:

    curl.exe -i https://<API_PUBLIC_DOMAIN>/healthz
    curl.exe -i https://<AI_PUBLIC_DOMAIN>/healthz
    curl.exe -i https://<WEB_PUBLIC_DOMAIN>/

Expected results:

1. API health check returns HTTP 200 JSON.
2. AI health check returns HTTP 200 JSON.
3. Web returns HTTP 200 HTML.
4. Web HTML contains "/assets/index-".
5. Web HTML does not contain "/@vite/client".

The Worker normally does not need a public domain. Verify it through its Railway
logs and health-check status.


12) TEST LOGIN

1. Open the Web public domain in a private browser window.
2. Register a test account.
3. Log in.
4. If login fails with a CORS error, check:

       API CORS_ORIGIN
       Web VITE_API_BASE_URL
       API public domain

5. Redeploy Web after changing VITE_API_BASE_URL.
6. Redeploy API after changing CORS_ORIGIN.


13) TEST A SMALL REPOSITORY INGESTION

1. Log in to the Web site.
2. Create or select an organization.
3. Add a small public GitHub repository.
4. Submit it for ingestion.
5. Watch the API logs for the request.
6. Watch the Worker logs for the queued job.
7. Confirm the status changes from QUEUED to RUNNING to COMPLETED.
8. Confirm analysis results appear in the Web UI.


14) TEST AN AUTHORIZED WEBSITE INGESTION

1. Use a website for which you have explicit authorization.
2. Submit the public URL.
3. Confirm the API accepts the request.
4. Confirm the Worker logs show the website crawl.
5. Confirm the crawl writes a site profile and crawl observations.
6. Confirm endpoint artifacts are shown in the repository details page.
7. Treat JavaScript-shell or verification/interstitial coverage as incomplete
   when reported by the application.


15) IF A SERVICE FAILS

API build fails with missing internal packages:

    Confirm API Root Directory is /
    Confirm Config-as-code path is /apps/api/railway.json
    Confirm the build log runs the workspace build command

Worker build fails with missing internal packages:

    Confirm Worker Root Directory is /
    Confirm Config-as-code path is /apps/worker/railway.json
    Confirm the build log runs the workspace build command

AI cannot be reached:

    Confirm AI is running
    Confirm AI_SERVICE_URL uses the AI private domain
    Confirm API, Worker, and AI share INTERNAL_JOB_TOKEN_SECRET

Web shows a blank page or calls the wrong API:

    Confirm VITE_API_BASE_URL was set before the Web build
    Redeploy Web after changing it
    Confirm the value is the API public HTTPS URL

Login returns HTML instead of JSON:

    Confirm the API public URL is used by VITE_API_BASE_URL
    Confirm API CORS_ORIGIN contains the exact Web public origin
    Confirm the browser is not using an old cached Web deployment


16) FINAL GO-LIVE CHECKLIST

Mark the deployment complete only when all are true:

    [ ] PostgreSQL is running
    [ ] Redis is running
    [ ] AI /healthz returns 200
    [ ] API /healthz returns 200
    [ ] Worker deployment is running
    [ ] Web returns production assets
    [ ] No service detects or runs a Procfile
    [ ] API, Worker, and AI share the same internal secret
    [ ] API and Worker reach the AI private domain
    [ ] Login works
    [ ] Small repository ingestion completes
    [ ] Authorized website ingestion completes
